# Packaging & distribution

This directory holds everything needed to distribute the Klardrop **desktop** app.
The version is driven entirely by the git tag: pushing `vX.Y.Z` (or running the
`Release` workflow with a version) builds the artifacts and publishes the GitHub
Release. Every download channel points at that release.

## Layout

```
packaging/
  install.sh                            # Linux installer (curl | bash) + in-app self-update source
                                         # supports --native, --omarchy, --qt, and --jvm flavors
  linux/
    klardrop.desktop                    # JVM-tarball application-menu entry ONLY (Exec rewritten
                                       # at install time). The native/Omarchy flavors ship their
                                       # own klardrop.desktop generated by install.sh -- do not
                                       # flip this one for those, or the other for this one.
    com.carlom.Klardrop.metainfo.xml    # AppStream metadata
    stage-native-tarball.sh             # stages klardrop-native-linux-{x64,arm64}.tar.gz
    test-omarchy-install.sh             # comprehensive test suite for native, Omarchy, and Qt flows
  homebrew/
    klardrop.rb                         # macOS cask template (@VERSION@ / @SHA256@ rendered by CI)
  aur/
    PKGBUILD                            # Arch klardrop-bin template (JVM desktop app)
    klardrop-native-bin/
      PKGBUILD                          # Arch klardrop-native-bin template (headless native engine)
    klardrop-omarchy/
      PKGBUILD                          # Arch klardrop-omarchy template (Omarchy shell integration)
      klardrop-omarchy-enable           # per-user activation script
      klardrop-omarchy-disable          # per-user deactivation script
    klardrop-qt-bin/
      PKGBUILD                          # Arch klardrop-qt-bin template (standalone Qt Quick frontend)
  README.md
```

## Channels

### Linux — `install.sh` (primary)

A single script, run straight from the terminal:

```sh
curl -fsSL https://raw.githubusercontent.com/carlonzo/klardrop/main/packaging/install.sh | bash
```

#### Flavors & Architecture Matrix

- **Native engine (`--native`, `--omarchy`, `--qt`):** Built for both **`x86_64`** (`x64`) and **`aarch64` / `arm64`** (`arm64`).
- **JVM desktop application (`--jvm`, `klardrop-bin`):** Published for **`x86_64` only**.

Flavors:
1. **Auto-detection (default):**
   When invoked without flavor flags on a clean install, `install.sh` checks if an Omarchy desktop environment is running (`command -v omarchy` succeeds). If present, it installs the **Omarchy native flavor** (`--omarchy`). If Omarchy is not found, it defaults to the native engine + standalone Qt Quick frontend (**Qt flavor**, `--qt`). No JVM is installed or required. Bare reinstall/upgrade on an existing installer-owned install preserves its previously selected flavor (including `--qt` and `--native`), even on Omarchy desktops.
2. **`--native` (generic headless native engine):**
   Installs only the two compiled binaries (`~/.local/bin/klardrop`, the Rust client, and `~/.local/bin/klardrop-engine`, the Kotlin/Native engine), the marker file, and the systemd user unit (`~/.config/systemd/user/klardrop.service`, `ExecStart=%h/.local/bin/klardrop-engine daemon`). Does **not** install desktop entries, MIME associations, Nautilus extensions, Omarchy shell plugins, menu items, or icons. Useful for generic Linux servers, headless nodes, non-Omarchy desktop environments, and automation.
3. **`--omarchy` (engine + Omarchy desktop integration):**
   Installs the native engine plus full integration into the Omarchy desktop shell: the `klardrop.omarchy` QML bar widget/quick panel, launcher helper (`klardrop-omarchy-open`), menu share helper (`klardrop-omarchy-share`), file-manager share helper (`klardrop-share-pick`), application menu JSONC entries, desktop files, Nautilus extension, and hicolor icons.
   The file-manager share callers (the `NoDisplay` "Open with…" desktop entry and the Nautilus "Send with Klardrop" action) exec `~/.local/bin/klardrop-share-pick` instead of the client. `klardrop share --pick` needs a real terminal on **both** stdin and stdout; GIO gives a `Terminal=false` .desktop entry and a `Gio.Subprocess` child plain pipes, so calling the client directly exits 2 and file-manager sharing does nothing. `klardrop-share-pick` starts `klardrop.service`, finds a terminal emulator (`$TERMINAL`, else `foot`, `kgx`, `gnome-terminal`, `alacritty`, `kitty`, `wezterm`, `xterm`) and re-runs the picker inside it. The Omarchy menu helper (`klardrop-omarchy-share`) deliberately does **not** use it: that one already runs from a terminal.
4. **`--qt` (engine + standalone Qt Quick desktop frontend):**
   Installs the native engine, standalone Qt Quick binary (`~/.local/bin/klardrop-qt`), desktop launcher (`~/.local/bin/klardrop-qt-launcher`), desktop entry (`~/.local/share/applications/klardrop.desktop`), and hicolor icons. Uses system Qt 6 runtime (baseline pinned to Ubuntu 24.04 Qt 6.4.2; requires `qt6-base`, `qt6-declarative`, QML modules including `QtQml` (`qml6-module-qtqml`), `Models` (`qml6-module-qtqml-models`), `WorkerScript` (`qml6-module-qtqml-workerscript`), and `qt6-wayland`). UI is only launched explicitly by the user (no UI autostart to respect daemon memory budget). Re-running `install.sh` on an existing `--qt` install preserves `--qt`.
5. **`--jvm` (JVM desktop application):**
   Forces installation of the universal JVM Compose Multiplatform desktop application (requires Java ≥ 21, x86_64 only), even when running on an Omarchy system.

Mutually conflicting flags (such as passing both `--native` and `--omarchy`, or `--jvm` and `--qt`) or unrecognized options are rejected immediately before any system changes.

Other flags:
- `--stable` (default) / `--nightly`: selects release channel.
- `--restart-daemon`: forces immediate daemon restart during upgrades (warns that active transfers will be aborted).
- `--uninstall`: removes the installed flavor.

#### Native Dependencies & Preflight Validation

Before making any filesystem or service mutations, `install.sh` verifies required dependencies:
- **Shared libraries (via `ldd`):** Both extracted native binaries (`bin/klardrop-engine` and `bin/klardrop`) are inspected with `ldd` (failure to execute `ldd` halts before mutation), each with the same actionable hints. Missing libraries trigger those commands:
  - Avahi (`libavahi-client`):
    - Arch / Omarchy: `pacman -S avahi`
    - Debian / Ubuntu: `apt install libavahi-client3`
    - Fedora: `dnf install avahi-libs`
    - Runtime service: `sudo systemctl enable --now avahi-daemon`
  - SQLite (`libsqlite3`):
    - Arch / Omarchy: `pacman -S sqlite`
    - Debian / Ubuntu: `apt install libsqlite3-0`
    - Fedora: `dnf install sqlite-libs`
  - OpenSSL 3 (`libssl`):
    - Arch / Omarchy: `pacman -S openssl`
    - Debian / Ubuntu: `apt install libssl3t64` (Ubuntu 24.04+, Debian 13) or `apt install libssl3` (Ubuntu 22.04, Debian 12)
    - Fedora: `dnf install openssl-libs`
  - libsystemd (`libsystemd`):
    - Arch / Omarchy: `pacman -S systemd-libs`
    - Debian / Ubuntu: `apt install libsystemd0`
    - Fedora: `dnf install systemd-libs`
- **System services & runtime diagnostics:**
  - `avahi-daemon`: Warns if the Avahi daemon is inactive (required for mDNS discovery) with `sudo systemctl enable --now avahi-daemon`.
  - Wayland clipboard: Warns if `wl-clipboard` (`wl-copy`/`wl-paste`) is missing under Wayland sessions.
  - `systemd --user`: Diagnoses user session bus availability. If systemd is inaccessible (e.g., containers, chroots, or non-systemd sessions), it warns and explains how to run the engine manually (`~/.local/bin/klardrop-engine daemon`) rather than failing.
  - `perl`: Checked before editing Omarchy menu files (used for non-destructive regex editing preserving user comments).

#### Safety Guards & Atomic Upgrades

- **Package manager protection:** `install.sh` queries `pacman -Qo`, `dpkg-query -S`, and `rpm -qf` for both `~/.local/bin/klardrop` and `~/.local/bin/klardrop-engine`. If either existing binary is owned by a system package manager, `install.sh` halts to prevent overwriting (or, on `--uninstall`, deleting) package-managed files.
- **Unrelated binary & service protection:** If `~/.local/bin/klardrop` or `~/.local/bin/klardrop-engine` exists without an installer marker or service unit, the installer refuses to overwrite or remove it. A symlink on the engine path is refused outright (the client path is the one legacy exception: a JVM app-image launcher symlink there is legitimate migration evidence). Unrelated service units are similarly protected from overwrite or removal independently of whether the binaries exist. In addition, explicit `--jvm --uninstall` refuses to delete an identified native install.
- **Running daemon / app detection:**
  - JVM app running: detected via `pgrep -f "klardrop.launcher="` before mutations, requiring the user to quit.
  - JVM install path rejects active native daemon (`klardrop.service` active or `klardrop.*daemon` running).
- **Atomic binary replacement:** Both binaries are written to sibling temporary files (`~/.local/bin/.klardrop-engine.tmp.<pid>` and `~/.local/bin/.klardrop.tmp.<pid>`) and only then moved into place via atomic rename (`mv -f`), avoiding `ETXTBSY` ("Text file busy") errors and never leaving a new client paired with an old engine (or the reverse).
- **Active transfer preservation (deferred restart):**
  When updating an already-running daemon, `install.sh` queries the daemon's local authenticated `/state` API (discovering the port and bearer token from `$XDG_RUNTIME_DIR/klardrop/control.json`).
  Inspection uses Python 3's standard library (`urllib.request` and `json`) to safely parse whitespace-tolerant JSON and verify:
  - `transfers == []` (no outgoing or active transfers)
  - `incoming == []` (no pending authorizations or incoming receives)
  - `pairingDialog is None` (no active pairing prompt; missing field defers)
  - `qrShare.active is False` (strictly boolean False; missing, null, or string state defers restart)
  - Bearer token is never printed in terminal output or exposed on command line `argv`.
  - **Verified idle:** Automatically reloads and restarts `klardrop.service` (`systemctl --user daemon-reload && systemctl --user restart klardrop.service`).
  - **Active transfers, uninspectable state, or missing python3:** Restart is deferred to protect in-flight transfers. The new binaries are installed at `~/.local/bin/klardrop-engine` and `~/.local/bin/klardrop`, and the installer instructs the user to run `systemctl --user restart klardrop.service` once transfers complete.
  - Specifying `--restart-daemon` overrides this and restarts immediately, with an explicit warning that ongoing transfers will be interrupted.

#### Systemd User Service Targets

The installer configures systemd `--user` units tailored to each flavor:
- **`--native` (generic headless):**
  Uses `WantedBy=default.target` with **no `After=default.target`**, ensuring the service starts reliably for headless/SSH sessions without creating a dependency ordering cycle in systemd.
- **`--omarchy` (desktop integration):**
  Uses `WantedBy=graphical-session.target` with **no `After=graphical-session.target`** (because `graphical-session.target` has default dependencies, an `After` directive creates an enabled-target ordering cycle). This provides graphical activation alongside the session without guaranteeing keyring readiness.

#### Scope & Uninstall

Native flavors (`--native` and `--omarchy`) are strictly **per-user** and refuse to run as root (`id -u == 0`).

Uninstall:
```sh
curl -fsSL https://raw.githubusercontent.com/carlonzo/klardrop/main/packaging/install.sh | bash -s -- --uninstall
```
Uninstall detects whether a native engine or Omarchy integration is installed and removes binaries, units, helpers, and plugins while **strictly preserving** user data and configuration: `~/.local/share/klardrop`, `~/.config/klardrop`, `~/.cache/klardrop`, and `~/.klardrop`.

For the JVM desktop app (`--jvm`), install locations remain:

| Scope | App-image | Launcher | Desktop entry | Icons |
|-------|-----------|----------|---------------|-------|
| user (default) | `~/.local/lib/klardrop` | `~/.local/bin/klardrop` | `~/.local/share/applications` | `~/.local/share/icons/hicolor` |
| root (`sudo`)  | `/opt/klardrop` | `/usr/local/bin/klardrop` | `/usr/share/applications` | `/usr/share/icons/hicolor` |

### macOS — Homebrew cask

`homebrew/klardrop.rb` is a cask template. On a stable release CI renders the
version + DMG checksum and pushes it to the `carlonzo/homebrew-klardrop` tap as
`Casks/klardrop.rb`. The DMG is unsigned, so the cask strips the quarantine flag on
install (see "macOS signing").

```sh
brew install --cask carlonzo/klardrop/klardrop
```

### Linux — native packages (AUR & package managers)

Klardrop provides packaging definitions under `packaging/aur/`:

| Channel | Type | Status | Description |
|---------|------|--------|-------------|
| AUR `klardrop-bin` | JVM desktop app | Published | Repackages the universal JVM desktop app into `/opt/klardrop` + `/usr/bin/klardrop`. Bumped by CI on every stable release (`yay -S klardrop-bin`). |
| AUR `klardrop-native-bin` | Native engine + CLI | Published | Repackages the native binaries for `x86_64` and `aarch64`, conflicts with `klardrop-bin`, declares runtime dependencies (`avahi`, `sqlite`, `openssl`, `systemd-libs`), subprocess optdepends (`curl`, `libnotify`, `wl-clipboard`, `libsecret`, `ffmpeg`, `qrencode`, `xdg-utils`), installs `/usr/bin/klardrop` (Rust client) and `/usr/bin/klardrop-engine` (engine), and installs `/usr/lib/systemd/user/klardrop.service` pointing to `/usr/bin/klardrop-engine daemon` (`WantedBy=default.target` with no `After=default.target`). |
| AUR `klardrop-omarchy` | Omarchy integration | Published | Minimal optional package providing the Omarchy shell plugin (bar widget & quick panel) to `/usr/share/klardrop/omarchy-plugin` and per-user activation scripts (`klardrop-omarchy-enable` / `klardrop-omarchy-disable`). Full application menu integration, file manager context actions, and Nautilus extensions are supplied by the full installer (`install.sh --omarchy`). |
| AUR `klardrop-qt-bin` | Standalone Qt Quick GUI | Published | Standalone Qt Quick desktop frontend package for Arch Linux (`packaging/aur/klardrop-qt-bin/PKGBUILD`). Precompiled binary package depending on `klardrop-native-bin`, `qt6-base`, `qt6-declarative`, providing and conflicting with `klardrop-qt`, and installing desktop entry + icons. |

> [!NOTE]
> All four packages are rendered and pushed by `.github/workflows/release.yml` on every stable release: the templates are filled with the tag version and the **real per-arch sha256 digests** of the published native tarballs (`SHA_X64` / `SHA_ARM64` in the `Render native PKGBUILDs + .SRCINFO` step), and any placeholder left unrendered fails the release. `yay -S klardrop-native-bin`, `yay -S klardrop-qt-bin` and `yay -S klardrop-omarchy` therefore install the current release, exactly like `yay -S klardrop-bin`.
>
> The only thing that gates the native push is whether the AUR repositories exist: each of the three is checked with `git ls-remote`, and a repository that has not been created yet is skipped with a warning instead of failing the release. Create the three repos once and they are maintained from then on.

The in-app and native self-updater inspects the binary via `pacman -Qo`, `dpkg-query -S`, or `rpm -qf` and refuses to overwrite package-managed binaries, directing users to their package manager instead.

### Headless engine vs Desktop GUI

- **Native Linux Engine (`--native`):** Headless background service. Provides `klardrop daemon` (forwards to `klardrop-engine`), `klardrop share --to <device-id> <files>`, the explicit `klardrop share --pick <files>` device picker used by the desktop entry, Nautilus action and Omarchy menu helper, and local CLI functionality.
  `klardrop-share-pick` is the terminal-spawning bridge used by the GUI callers (desktop entry + Nautilus), which have no tty of their own.
- **Omarchy Desktop (`--omarchy`):** UI is provided by the native `klardrop.omarchy` QML shell plugin.
- **Standalone Qt Quick Frontend (`--qt`):** Standalone Qt Quick desktop frontend connecting to the local daemon over loopback HTTP. Default desktop GUI on non-Omarchy Linux systems. Launched explicitly by user, minimizes to system tray if available, single-instance activation.
- **JVM Compose Desktop (`--jvm` or `klardrop-bin`):** Legacy universal JVM desktop application bundling the Compose Multiplatform UI (`--jvm` explicit compatibility flag). Maintained for backwards compatibility and system-wide installs; the published package repository channel remains `yay -S klardrop-bin` (the legacy JVM app), while `klardrop-native-bin` / `klardrop-qt-bin` are the current native channels.

### Testing

`packaging/linux/test-omarchy-install.sh` exercises the complete installer matrix inside a temp `HOME` with external commands stubbed out:
- Native engine and Omarchy integration installs and idempotent re-installs
- Generic headless `--native` (verifying no Omarchy files or shell hooks are installed)
- Both architectures (`x86_64` and `aarch64`/`arm64`)
- Deferred restart on active transfers vs automatic restart when idle vs explicit `--restart-daemon`
- Dependency missing preflights via fake `ldd` (leaves existing installation untouched)
- `systemd --user` unavailable diagnostic guidance
- Flag contradiction and unknown flag rejections
- JVM migration (rejection when running, clean migration when stopped)
- Refusal to overwrite package-managed binaries
- Hermetic `systemd-analyze --user verify` on the generated unit (`WantedBy=default.target`)
- Pair-install safety: a **directory** on `~/.local/bin/klardrop` or `klardrop-engine` is refused before any mutation (`mv -f <file> <dir>` would otherwise bury the binary and still exit 0), and a client swap that cannot complete rolls the engine back instead of leaving a new engine beside an old client
- The **shipped** Qt launcher (`packaging/linux/klardrop-qt-launcher.sh`, the single file the stager and the fixtures both copy) is asserted to carry the post-split `klardrop-engine daemon` hints
- Downloads go through a stubbed `curl`: a missing `.sha256` sidecar, and a sidecar whose digest does not match the tarball, are both refused — with a matching sidecar as the positive control

### Windows — MSI

Download the `.msi` from the [latest release](https://github.com/carlonzo/klardrop/releases/latest).
Windows still uses `jpackage` with a **bundled JRE** — users are not expected to
have Java installed. Mac is the native app (Homebrew cask / DMG); it is unchanged.

The Rust CLI ships as a **sibling release asset**, `klardrop-cli-windows-x64.zip`,
published under its own `windows-cli` key in `latest.json` — deliberately *not*
inside the MSI. jpackage signs what it builds, so a file dropped into the install
directory afterwards invalidates the installer's signature.

**The name collides, and that is the one thing to be careful about.** The MSI
installs a jpackage launcher that is itself called `klardrop.exe` at
`C:\Program Files\Klardrop\app\klardrop.exe` — that is the GUI. The zip contains a
different `klardrop.exe`: the native CLI. Unzip it to a directory that is **not**
the jpackage `app` directory, or the GUI will shadow it on `PATH`:

```powershell
# anywhere that is on PATH and is NOT C:\Program Files\Klardrop\app
Expand-Archive klardrop-cli-windows-x64.zip -DestinationPath "$env:LOCALAPPDATA\Klardrop\bin"
& "$env:LOCALAPPDATA\Klardrop\bin\klardrop.exe" devices
```

Both binaries talk to the same running desktop app through
`%LOCALAPPDATA%\Klardrop\control.json`; neither starts an engine of its own. The
app's own update dialog links the CLI when a build published no MSI
(`UpdateChecker.ASSET_WINDOWS_CLI`). On macOS the CLI does ship *inside* the DMG:
signing and notarization happen on the final image, so the signed CLI travels
with it.

## The native Linux tarball

`packaging/linux/stage-native-tarball.sh` builds
`klardrop-native-linux-{x64,arm64}.tar.gz` from two binaries with deliberately
distinct names:

- **`bin/klardrop`** — the Rust client (`cli-rust/`), the user-facing CLI. It talks
  to a running engine over the local control file and does not embed one.
- **`bin/klardrop-engine`** — the Kotlin/Native engine (`:cli`,
  `klardrop-engine.kexe`), which owns `daemon`, `listen`, and the local control
  plane. Splitting the names is what makes it impossible for a client invocation
  to start a second engine by accident.

The stager fails closed: it refuses to build a tarball without either binary
(`cargo build --locked --release` for the client), verifies the ELF architecture
of *every* binary it stages, and aborts if anything named
`klardrop-fixture-daemon` (a `cli-rust` test-only binary) reaches the stage tree.

```
klardrop-native-linux-x64/
    bin/klardrop                       # Rust client
    bin/klardrop-engine                # Kotlin/Native engine
    bin/klardrop-qt                    # Qt Quick frontend
    bin/klardrop-qt-launcher           # starts klardrop.service, execs klardrop-qt
    share/klardrop/applications/klardrop.desktop
    share/klardrop/omarchy-plugin/      # Omarchy QML plugin
    share/klardrop/icons/{128,256}x{128,256}/klardrop.png
    VERSION
```

## The universal Linux tarball

The release workflow builds a tarball, `klardrop-linux-x64.tar.gz`, consumed by
both the install script and the in-app self-updater. It does **not** ship a JRE:
`bin/klardrop` is a shell wrapper that execs system `java` (≥ 21). Bytecode is
compiled with `jvmTarget = JVM_21`. Internal layout:

```
klardrop-linux-x64/
  klardrop/
    bin/klardrop                        # shell wrapper (not a jpackage native launcher)
    lib/app/                            # ProGuard'd jars + libskiko-linux-x64.so
                                        # NO lib/runtime/
  klardrop.desktop
  com.carlom.Klardrop.metainfo.xml
  icons/<size>/klardrop.png             # 32, 64, 128, 256, 512
  icons/scalable/klardrop.svg           # scalable source (theme prefers it)
```

`packaging/linux/klardrop.desktop` is the entry for **this** (JVM) tarball only, where
`bin/klardrop` is the JVM launcher and `Exec=klardrop %F` opens the app. The native
and Omarchy flavors get a *different* `klardrop.desktop`, generated by
`install.sh` (and, for `--qt`, from `share/klardrop/applications/klardrop.desktop`
inside the native tarball). Never copy one over the other.

The wrapper sets `-Dklardrop.launcher=<absolute path to itself>` so the in-app
updater still sees the script inside `/opt/klardrop` or `~/.local/lib/klardrop`
rather than `/usr/bin/java`.

The `.desktop` uses `Icon=klardrop` — a theme *name*, not a path — so it resolves
to whichever `klardrop.*` the installer dropped into `hicolor` (the SVG at any size,
PNGs as fallback). It works the same for a `/opt` or a `~/.local` install.

## In-app updates

On launch — and every 6 hours after that, since a desktop session routinely outlives
several releases — the app fetches `releases/latest/download/latest.json` (or the
nightly manifest, for a nightly build) and compares its semver to the running build.

Three surfaces show the result:

- **The banner** on the discovery screen, when and only when an update exists.
  Dismissible per version.
- **Settings → Updates**, always: the running version, how this copy was installed,
  the live check state, and a **Check for updates** button. This is where a user who
  simply wonders "am I current?" gets an answer.
- **The tray menu**, so an update is visible while the window is hidden — which, for
  a background share target, is most of the time.

What the update button does depends on how this copy was installed. Klardrop detects
that at runtime (`detectInstallChannel`) rather than assuming, because every system
package manager owns its own files: writing over them would leave the package database
lying about what is installed.

| Detected channel | How it's detected | What the app offers |
|------------------|-------------------|---------------------|
| Linux `install.sh`, user-writable | launcher under `~/.local/lib/klardrop` or `/opt/klardrop` | **Self-update**: downloads the tarball, verifies sha256, stages it, then a **Restart** button swaps the app-image and relaunches — no terminal, no sudo |
| Linux `install.sh`, root-owned `/opt` | as above but not writable | the one-line `curl … \| bash` reinstall |
| Debian / Ubuntu | `dpkg-query -S` owns the launcher | `curl -fsSLO <deb> && sudo apt install ./<deb>` |
| Fedora / openSUSE | `rpm -qf` owns the launcher | `curl -fsSLO <rpm> && sudo rpm -Uvh ./<rpm>` |
| Arch | `pacman -Qo` owns the launcher | `yay -S klardrop-bin` (or `yay -S klardrop-native-bin` on native) |
| Flatpak | `$FLATPAK_ID` / `/.flatpak-info` | `flatpak update com.carlom.Klardrop` |
| Snap | `$SNAP` or a `/snap/…` launcher | `sudo snap refresh klardrop` |
| AppImage | `$APPIMAGE` or a `/tmp/.mount_…` launcher | download link |
| Nix | launcher in `/nix/store` | `nix profile upgrade klardrop` |
| macOS Homebrew | `brew list --cask klardrop` | `brew upgrade --cask klardrop` |
| Unsigned DMG / Windows MSI / unknown | fallthrough | download link for the platform asset |

Flatpak, Snap, AppImage and Nix are detected but not published by this repo — if a
downstream packager ships one, the app gives that channel's own upgrade command
instead of misdirecting the user to a tarball.

Commands are offered as copy-to-clipboard (the app never runs a privileged command
itself). A failed self-update falls back to the channel's command, and an "update
available" state is never hidden by a later failed check.

The keep rules in `desktop/rules.pro` ensure `latest.json` still parses in the
minified release build; the release workflow boots the minified app-image as a gate.

## macOS signing

Signing is conditional on the Apple secrets being configured, and the macOS job
does the full chain when they are: `codesign` of the app and the CLI,
`notarytool submit --wait`, and `xcrun stapler staple` on both the `.app` and the
DMG, writing `macos-verified.txt` as the marker. `latest.json` only advertises
the `macos` key when that marker exists, so an unsigned CI build is never
presented as a verified download channel.

Without the secrets the DMG ships **unsigned**: Gatekeeper blocks it on first
launch and the user must right-click → Open (or
